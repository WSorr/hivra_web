About Hivra

Hivra is a Person-First Runtime.

We call it a reference implementation of a person-owned digital principal. The Capsule is not an account, platform, or social profile. It is a stable continuity layer where a person’s state, memory, and trust context are anchored.

Current architecture

Core concepts are intentionally small and strict. Capabilities are attached through explicit flows and can be replaced without rewriting person continuity.

The inversion

Reference model and vocabulary.

We do not model an abstract social graph first. We model a person as the source of continuity, and then connect applications, transports, and services to it through controlled, inspectable surfaces.

Person / Capsule

Capsule is the personal runtime anchor — persistent and identity-rich but not an account in a platform sense.

Persistent local runtime

The runtime is continuously present and can carry state across devices and sessions.

Replaceable capabilities

Core does not own a fixed app surface. Capabilities can evolve and rotate while continuity remains intact.

Capsule boundaries

What Capsule owns.

Only the continuity layer: data that should stay stable with the person even when capabilities change.

Continuity

A durable thread that ties identity and state over time.

Authenticated history

Evidence that records state transitions and key decisions in the trust layer.

Core state

Stable anchors used as a root for local validation and reconciliation.

Bounded capability context

Current state defines which capability calls can be accepted from which source.

Adapter contracts

Ports for external services are not merged into core identity; they are attached as replaceable interfaces.

Evidence policy

Operationally, the core layer remains responsible for what is retained and what is not.

What Capsule does not mean

Hard guardrails.

Not an account A Capsule can use accounts, but it is not itself a provider account.

Not a social graph node We do not treat every relation as a social edge with implicit privilege.

Not a wallet Financial modules are capabilities, not the identity core.

Not a transport identity Network protocols and endpoints are pluggable, not canonical.

Not an app container Applications are clients of the runtime and can be replaced without replacing a person.

Trust layer

Slots, Starters, Invitations, and Relationships.

Trust is separate from the definition of Hivra itself. These are optional but important mechanisms that connect people and services through scoped consent and explicit path setup.

Slots

Structured entry points for trusted connectivity.

Starters / Invitations

Consent-first entry mechanisms used to open a trust path.

Relationships

Observed outcomes of trust establishment, not the core identity definition.

Capabilities and adapters

What applications can and cannot own.

Capabilities are composable services. We can add, retire, or replace them while keeping core continuity untouched.

Runtime plugins

Chat, AI, trading tools, agents, and similar capabilities are loaded as modules.

Replaceability

Any capability can be swapped if it keeps expected contracts and does not break continuity.

Evidence boundary

Effects and receipts stay tied to the external service policy and are not merged back as identity claims.

External world

Transport is always an adapter.

Protocols and providers are interchangeable as long as they respect capability contracts. Core truth remains person-bound.

Transport adapters

Wiring for protocols, APIs, and networks stays replaceable.

Evidence separation

Activity logs, proofs, and attestations are structured at boundaries where trust is delegated.

No protocol lock-in

Loss of a transport does not erase person continuity.

Why this matters

Applications become replaceable assets.

Person continuity first A core state survives app migration, provider migration, and service churn.
Smaller blast radius Compromise in one adapter does not automatically corrupt person continuity.
Composable future New modules can be introduced without redesigning the identity layer.
Current architecture

What Hivra does today.

This section intentionally describes implemented behavior only.

Implemented in current stack

  • Person-first continuity model anchored in Capsule.
  • Core state, authenticated history, and capability context tracking.
  • Starters + invitations + relationship path for trust setup.
  • Adapters for transports and external modules with replaceable interfaces.

Intended but not implemented as core semantics

  • Any claim that "bounded authority forwarding" or lifecycle inheritance is already a complete warrant protocol.
  • Directional/hierarchical trust graph semantics as default behavior.
Research direction

2026 → 2030 hypothesis track.

These are forward-looking assumptions, not claims of current implementation.

Agent identity is execution-first.

Intent-first interaction.

Local-first intelligence.

On-device stacks move toward first-class planning, safety, and context operations.

Blockchain as selective infrastructure.

Not every interaction must be on-chain; settlement and audits can stay selective.
